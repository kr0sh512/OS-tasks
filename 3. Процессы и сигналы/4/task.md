# Процессы и сигналы: убийство до чтения

Источник: `Test_20251109.md`, задание № 8, вариант C.

Что будет выведено на стандартный вывод? Перечислите все варианты, включая вывод перед вечной блокировкой. Все вернувшиеся системные вызовы считаются успешными; заголовочные файлы опущены. Предполагаются POSIX-процессы, блокирующий канал без посторонних участников и сигналов, неделимые однобайтовые записи на стандартный вывод. Доставка отправленного сигнала может происходить позже возврата `kill`: этот вызов сам по себе не ожидает завершения адресата.

Типографские кавычки исходника заменены на обычные кавычки C; иной код не изменён.

```c
int main(void) {
    pid_t pid;
    int fd[2];
    char x[] = "abc";
    pipe(fd);
    if ((pid = fork()) == 0) {
        write(1, x, 1);
        x[0] = 'f';
        write(fd[1], x, 2);
        x[0] = 's';
    } else {
        kill(pid, SIGKILL);
        read(fd[0], x, 2);
    }
    write(1, x, 1);
    return 0;
}
```

Уточните роль незакрытых дескрипторов и различие между отправкой сигнала и ожиданием завершения процесса.

---
# решение

Полное множество завершившихся вариантов в модели с асинхронной доставкой `SIGKILL`:

```text
af
asf
afs
```

Каждая запись здесь — последовательность байтов без завершающего перевода строки. Кроме того, возможна вечная блокировка родителя с одним из двух окончательных префиксов:

```text
<пустая строка>
a
```

Если ребёнок убит до записи в канал, родитель ждёт данные бесконечно. Он сам всё ещё держит открытым `fd[1]`, поэтому после смерти ребёнка в канале остаётся писатель: EOF не наступает. Если ребёнок не успел выполнить первую запись на экран, префикс пустой; если успел только её, префикс равен `a`. Успех уже вернувшихся вызовов не исключает такого зависания: блокирующий `read` не вернулся и не сообщил ошибку.

Если запись `fb` в канал состоялась, родитель получает оба байта и затем печатает `f`. До записи в канал ребёнок обязательно напечатал `a`. Атомарная двухбайтовая запись в блокирующий канал не больше `PIPE_BUF`, отсутствие других читателей и обрабатываемых сигналов исключают здесь получение только одного из этих байтов.

Если финальная запись ребёнка не состоялась, получаем `af`. Если состоялась, два финальных события вывода не упорядочены ожиданием: возможны `asf` и `afs`. В частности, `kill` может уже вернуться в родителе, но ребёнок ещё не завершиться: доставка сигнала адресату и завершение его уже выполняющегося системного вызова не являются ожиданием в родителе. Родитель способен напечатать `f` раньше, чем станет видимым уже начатый ребёнком вывод `s`.

В более сильной, дополнительной учебной модели, где `kill` синхронно уничтожает ребёнка в момент своего выполнения и все остальные вызовы — неделимые шаги, `afs` исключается: перед чтением ребёнок уже мёртв. Это **не** гарантия POSIX `kill`, и без явного принятия такой модели сужать ответ до `af` и `asf` нельзя. В вариантах A, B из того же источника такое сужение обеспечивается настоящим `wait`, отсутствующим здесь.

Строки `a` и пустая строка в данном ответе обозначают именно незавершившееся исполнение, а не нормальное завершение программы. Если исходную фразу «все вызовы успешны» понимать как требование возврата каждого вызова, зависшие исполнения не удовлетворяют этому дополнительному требованию; ошибка `read` от этого не возникает.
