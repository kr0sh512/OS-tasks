# И целого мьютекса мало

Проанализируйте следующий фрагмент C. Заголовки `<pthread.h>` и `<stdio.h>` опущены.

```c
int counter = 0;
pthread_mutex_t mutex = PTHREAD_MUTEX_INITIALIZER;

void func1(void* arg) {
    pthread_mutex_lock(&mutex);
    printf("A%d", ++counter);
    pthread_mutex_unlock(&mutex);
    pthread_exit(NULL);
}

void func2(void* arg) {
    pthread_mutex_lock(&mutex);
    printf("B%d", ++counter);
    pthread_mutex_unlock(&mutex);
    pthread_exit(NULL);
}

void func3(void* arg) {
    printf("C%d", ++counter);
    pthread_exit(NULL);
}

int main(void) {
    pthread_t t1, t2, t3;
    pthread_create(&t1, NULL, func1, NULL);
    pthread_create(&t2, NULL, func2, NULL);
    pthread_create(&t3, NULL, func3, NULL);
    pthread_join(t1, NULL);
    pthread_join(t2, NULL);
    pthread_join(t3, NULL);
    printf("D%d\n", counter);
    return 0;
}
```

В исходнике заявлены успешность системных вызовов, атомарность операций и отсутствие буферизации. Требуется определить, существует ли у реальной программы C конечный корректно определённый список выводов, и объяснить роль мьютекса.

Для отдельной учебной интерпретации явно примите следующие соглашения: функции нитей имеют корректный тип `void *(*)(void *)`, а **весь** оператор `printf("X%d", ++counter)` вместе с увеличением счётчика и выводом — одно атомарное действие в последовательно согласованной абстрактной машине. Перечислите выводы этой модели. Это дополнительная модель; обычный C таких свойств составному выражению не предоставляет.

# решение

## Реальная программа C

Все три функции нитей имеют несовместимый с `pthread_create` тип: возвращают `void` вместо `void *`. Компилятор должен диагностировать передачу несовместимого указателя на функцию. У исходника уже по этой причине нет гарантированного переносимого исполнения.

Даже после механического исправления типов остаётся гонка данных. `func1` и `func2` синхронизируются между собой, но `func3` изменяет тот же обычный `int counter`, не захватывая мьютекс. Потокобезопасность или атомарность вывода в `stdio` не превращает вычисление аргумента `++counter` в защищённый доступ. Следовательно, в C после исправления типов поведение всё равно неопределено; перечислять конечный список всех реальных выводов некорректно.

`pthread_join` обеспечивает ожидание завершения нитей перед последним выводом, но не исправляет гонку, произошедшую между нитями ранее. Исправление потребовало бы согласованной защиты **всех** доступов или другого явно определённого способа синхронизации.

## Явно заданная учебная модель

Атомарные действия `A`, `B`, `C` увеличивают счётчик с `0` до `3`; номер после буквы равен порядковому номеру действия. Мьютекс не запрещает ни одного из шести порядков этих трёх действий: операции `A` и `B` в любом случае выполняются по одной. После всех `join` действие `D` печатает `3`.

**Ровно шесть** строк; каждая оканчивается переводом строки:

```text
A1B2C3D3
A1C2B3D3
B1A2C3D3
B1C2A3D3
C1A2B3D3
C1B2A3D3
```

Это полный список только при атомарности составных операторов, оговорённой в условии учебной модели, а не результат выполнения исходной программы с гонкой данных.
