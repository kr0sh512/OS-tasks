# Процессы и сигналы: задача со звёздочкой

Источник: `Test_20251109.md`, «Задача со звёздочкой».

Начальная иерархия процессов:

```text
A
└── B
```

В программе процесс A создаёт ребёнка B. Считается, что `printf` работает атомарно и без буферизации, все обращения к системным функциям успешно отрабатывают. Перечислите все возможные комбинации значений, выводимых на стандартное устройство вывода. Заголовочные файлы опущены.

```c
int x = 3;

void hlr(int sig) {
    x = 5;
}

int main(int argc, char **argv)
{
    signal(SIGKILL, hlr);
    signal(SIGINT, hlr);

    int fd[2];
    pipe(fd);
    pid_t pid;

    int a = 4;
    if ((pid = fork()) == 0) {
        kill(getppid(), SIGINT);
        printf("%d\n", a);
        read(fd[0], &a, sizeof(a));
    } else {
        write(fd[1], &x, sizeof(x));
        kill(pid, SIGKILL);
    }

    printf("%d %d\n", getpid(), a);

    return 0;
}
```

Не исправляйте программу молча: сначала проверьте совместимость предпосылок с POSIX и правилами C. Если используете дополнительную учебную модель, сформулируйте её отдельно. Численные PID неизвестны: обозначайте их символически; PID усыновителя осиротевшего ребёнка обозначайте R, не предполагая безусловно R = 1.

---
# решение

## Буквальная постановка

Универсального списка вывода для программы с заявленным безусловным успехом всех вызовов **не существует**.

1. `SIGKILL` нельзя перехватить или игнорировать. В POSIX попытка `signal(SIGKILL, hlr)` завершается неуспешно: возвращается `SIG_ERR`, устанавливается `errno == EINVAL`. Следовательно, требование успеха всех обращений к системным функциям противоречит первой строке `main`. Это верно независимо от расписания.
2. `x` — обычный глобальный `int`, не `volatile sig_atomic_t` и не подходящий lock-free атомарный объект. Асинхронный обработчик обращается к нему присваиванием `x = 5`. Это не соответствует ограничениям ISO C на доступ обработчика к объектам со статическим временем хранения. При асинхронном вызове обработчика нельзя выводить переносимый результат из стандарта C. Тот факт, что машинная запись `int` на конкретной платформе часто атомарна, сам по себе не устраняет проблему языка.
3. Даже замена типа на `volatile sig_atomic_t` не сделала бы безоговорочным предположение о едином снимке значения, передаваемого `write` через адрес: правила взаимодействия сигнала с чтением представления объекта требуют отдельного анализа. В исходнике такой модели нет.

Если понимать «системные вызовы» узко, не включая интерфейс `signal`, первый вызов всё равно завершается ошибкой, а не устанавливает обработчик `SIGKILL`; второй пункт остаётся независимой проблемой. Возвращаемое значение первой регистрации в коде не проверяется, но игнорирование ошибки не превращает её в успех.

Также в переносимом POSIX `pid_t` не обязан совпадать с `int`, тогда как `%d` требует именно `int`. В обычной Linux-модели `pid_t` совместим с `int`; далее явно используется эта модель, а не утверждение о любом POSIX-окружении.

## Отдельная учебная модель

Следующее — не результат устранения ошибок без оговорки, а полный ответ для явно усиленных предпосылок:

- платформа Linux с `pid_t`, совместимым с `int`;
- неуспешная регистрация обработчика `SIGKILL` признаётся исключением из условия об успехе; она ничего не меняет;
- обработчик `SIGINT` установлен и сохраняется; присваивание `x = 5` и получение значения `x` для единственной записи в канал считаются неделимыми действиями абстрактной машины, без неопределённого поведения C;
- запись и чтение одного `int` через канал передают целиком одно значение, 3 либо 5; посторонних читателей и писателей нет;
- отправка сигнала и его доставка различаются: доставка `SIGKILL` может произойти на любом последующем шаге ребёнка, но после неё он больше ничего не выполняет; допускается завершение ребёнка до доставки;
- вывод каждого `printf` неделим, отсутствует буферизация и посторонний вывод; рассматриваются справедливые исполнения с завершением всех оставшихся живых процессов;
- если `getppid()` уже возвращает R, успешный `kill(R, SIGINT)` не создаёт дополнительных событий в рассматриваемой паре процессов. R не отождествляется с A или обязательно с PID 1.

Обозначим численные PID процессов A и B как `P` и `C`. Введём целые строки вывода:

```text
P4 := строка "P 4\n"
B4 := строка "4\n"
B3 := строка "C 3\n"
B5 := строка "C 5\n"
```

Здесь `P` и `C` в кавычках означают подстановку соответствующего десятичного PID, а не печать этих букв. Полное множество в этой учебной модели задаётся девятью последовательностями строк:

```text
P4
B4 P4
P4 B4
B4 B3 P4
B4 P4 B3
P4 B4 B3
B4 B5 P4
B4 P4 B5
P4 B4 B5
```

Пробелы между обозначениями в этом перечислении означают конкатенацию целых строк, не дополнительные символы вывода.

Доказательство полноты: локальное `a` родителя всегда 4, и родитель обязательно печатает ровно `P4`. Ребёнок сначала, если не убит раньше, печатает `B4`; после успешного чтения он может напечатать ровно одну из строк `B3`, `B5`. Его первая печать обязательно предшествует второй. Других строк нет. До родительского `write` значение `x` либо остаётся 3, либо меняется обработчиком на 5. Получаются ровно два возможных значения во второй строке ребёнка. При отсутствии `wait` между родительской строкой и строками ещё не завершённого ребёнка дополнительного порядка нет: доставка `SIGKILL` может быть отложена. Каждая из трёх перестановок `P4` с упорядоченной парой `B4`, `B3` или `B4`, `B5` достижима в принятой абстрактной машине. Если ребёнок уничтожен раньше второй печати, остаются первые три последовательности.

Если дополнительно, вопреки общей семантике POSIX, считать `kill` синхронным уничтожением адресата, множество сужается до `P4`, `B4 P4`, `B4 B3 P4`, `B4 B5 P4`. Это другой набор предпосылок: его нельзя выдавать за ответ для асинхронного сигнала.

Сам `SIGKILL` никогда не устанавливает `x = 5`: это может делать только обработчик `SIGINT`. После `fork` адресные пространства различны. Если ребёнок послал `SIGINT` уже усыновителю R, родительское `x` от этого не меняется. Ни в буквальной, ни в учебной постановке конкретные численные PID не определены.
